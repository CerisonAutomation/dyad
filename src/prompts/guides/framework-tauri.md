# Tauri desktop migration and security

Tauri can preserve an existing web frontend while using Rust and a system WebView. It is not an Electron compatibility layer. Before migration, inventory Electron imports and IPC, preload contracts, BrowserWindow/webContents usage, custom protocols, menus, clipboard, credentials, updates, terminal processes, database bindings, previews and browser automation. Preserve user data and provider/subscription selection.

- Prefer an incremental shell/bridge prototype over an unrequested rewrite. A packaged Node sidecar can retain provider SDKs and existing backend logic; it still ships a Node runtime and native dependencies. Specify typed messages, versioning, request IDs, cancellation, timeouts, restart policy and ownership/cleanup. Avoid broadly exposed unauthenticated localhost control servers.
- For Tauri 2, inspect tauri.conf.json, Cargo dependencies, plugin versions and capabilities. Expose the least privilege per command/window. Validate arguments, paths and authorization inside native commands. Never give generated app previews or remote pages broad shell/filesystem privileges. Keep secrets out of frontend bundles and logs.
- Do not assume Tauri 1 configuration or window.tauri APIs apply to Tauri 2. Read version-matched invoke/event/plugin documentation. WebKitGTK on Linux, WKWebView on macOS and WebView2 on Windows have differences that require target checks. Linux still needs system WebView dependencies.
- A smaller host shell does not eliminate an automation browser or guarantee lower total RAM. Measure installer size, cold startup, idle/active memory, streaming responsiveness and cleanup on the same workload, including sidecars/WebViews.
- Verify native commands and failed IPC, cancellation, malicious paths, sidecar crashes, clipboard and deep links, plus real packaged startup on requested platforms. Web-only mocks are not desktop integration evidence; use a minimal virtual display/desktop CI when necessary.
